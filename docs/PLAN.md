# План работ

Записано 3 ноября 2026. Пункты идут в рекомендуемом порядке: сначала структура, потому что от неё зависят пути во всём остальном.

## 1. Навести порядок в архитектуре

**Задача:** чёткое разделение на расширение, нативное приложение и общий код.

Сейчас общий код лежит внутри расширения (`extension/src/shared.js`, `page.js`, `content.js`, `extension/fonts`), а `desktop/` забирает его оттуда при сборке. Предлагаемая структура:

```
shared/             код джема и шрифты: один на расширение и приложение
extension/          только расширение: manifest, попап, виджет, фоновый скрипт
native/             приложение Electron (сейчас desktop/)
services/rooms/     сервер комнат (сейчас server/)
services/links/     сервис ссылок (сейчас links/)
deploy/  docs/  tools/  store/
dist/               все сборки, см. пункт 2
```

**Что учесть:**
- Chrome загружает распакованное расширение только из одной папки и не видит файлы выше неё. Если общий код уедет в `shared/`, для разработки понадобится сборка в `dist/extension/` или ссылки на файлы. Сейчас сборка для разработки не нужна.
- Переезжают пути в `tools/build.sh`, `desktop/scripts/bundle.js`, CI, задачах VS Code, `deploy/`, `CONTRIBUTING.md` и документации.
- Папка `/opt/...` и контейнеры на сервере от структуры репозитория не зависят, но скрипты деплоя нужно поправить и проверить.
- Файлы переносим через `git mv`, отдельным коммитом и без изменений кода, чтобы сохранить историю.

**Готово, когда:** собираются и работают расширение и приложение, тесты и CI зелёные, в расширении и приложении нет копий общего кода.

## 2. Одна папка со сборками

**Задача:** всё собранное лежит в одном месте. Сейчас сборки разбросаны: `dist/`, `dist/friends/` и `desktop/dist/`.

```
dist/
  extension/        расширение для Chrome (zip)
  native/           mac-apple-silicon.dmg, mac-intel.dmg, windows.exe
```

Служебные файлы `electron-builder` не должны смешиваться с готовыми файлами. Задачи `build` и `build-all` переводятся на новые пути. `dist/` остаётся вне git.

## 3. Сборка и релиз при каждом пуше в `main`

**Почему на GitHub всё ещё 1.1.0:** значок показывает последний релиз, а релиз создаётся только по тегу `v*`. Последний тег `v1.1.0`, хотя манифест уже `1.2.16`. Приложение (`desktop.yml`) собирается только вручную или по тегу `desktop-v*` и попадает в артефакты запуска, а не в релизы.

**Локальные сборки на GitHub не попадают:** `dist/` не в git. Собирать должен GitHub Actions: Mac и Windows на своих машинах, публичному репозиторию это бесплатно.

**Задача:** пуш в `main` собирает расширение и приложение и обновляет релиз.

**Что нужно решить:**
- Новый номер релиза на каждый пуш или один постоянно обновляемый релиз. Рекомендую: тег по версии из манифеста, а при той же версии обновлять файлы существующего релиза.
- Как показывать две версии: у расширения и приложения они разные.
- Значки README: у Chrome Web Store своя версия, она обновляется только публикацией в магазин. Это отдельный ручной шаг, CI его не заменит.

## 4. Страница на GitHub и кнопка «Скачать сборки»

**Задача:** рядом с «Установить из Chrome Web Store» кнопка «Скачать сборки». За ней два раздела с прямыми ссылками:

- **Расширение для Chrome**
- **Нативный плеер:** Mac Apple Silicon, Mac Intel, Windows

**Ограничение:** внутри релиза GitHub папок нет, там плоский список файлов. Поэтому роль папок сыграет страница `docs/DOWNLOADS.md` (или раздел README) с такими разделами. Для постоянных ссылок нужны имена файлов без версии: `releases/latest/download/babushkin-jam-mac-apple-silicon.dmg`.

**Также:**
- заметная ссылка на все релизы;
- инструкция для первого запуска: приложение не подписано, поэтому Mac и Windows предупредят;
- проверить остальные значки: `Node.js 18+` устарел, сервису ссылок нужен 22.13.
